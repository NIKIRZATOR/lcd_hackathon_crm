# RTK EduFlow: схема данных и seed

Документ описывает фактическую архитектуру проекта на 27 сентября 2026 года. Он составлен по `docker-compose.yml`, моделям SQLAlchemy, API и `backend/scripts/seed_demo_data.py`. Его цель — дать безопасную опору для расширения демо-данных: какие сущности создавать, в каком порядке и какие показатели допустимо имитировать.

## 1. Контуры хранения и сервисы

| Контур | Где хранится | Назначение | Источник / кто пишет |
|---|---|---|---|
| Операционные данные CRM | PostgreSQL, БД `rtk_eduflow` | Все таблицы ниже: каталог, программы, workflow, сигналы, отчёты, аудит | FastAPI, seed, worker |
| Аутентификация | Keycloak, отдельная БД PostgreSQL `keycloak` | Учётные записи, сессии, токены и настройки realm | Keycloak; CRM хранит локальный профиль пользователя |
| Очередь | Redis, DB `0`, очередь `reports` | Только асинхронные задания на построение отчётов | Reports API пишет, `worker` читает |
| Файлы | MinIO (S3-совместимое хранилище) | Файлы workflow, импорты, готовые отчёты, документация | API и report worker |
| Клиент | Vite/React frontend | Не является источником бизнес-данных; запрашивает REST API | Браузер |

MinIO создаёт четыре bucket: `workflow-files`, `imports`, `reports`, `documentation`. В таблице `files` находятся метаданные и ссылка на объект; содержимое файла в PostgreSQL не хранится.

```text
React UI ──REST/JWT──> FastAPI ──SQLAlchemy──> PostgreSQL (rtk_eduflow)
                            │                         │
                            ├──> MinIO <── File ───────┘
                            ├──> Redis reports queue ─> report worker ─> MinIO
                            └──> Keycloak (проверка JWT)

Внешний файл/fixture ─> imports/integrations ─> IntegrationSignal
                     ─> explicit mapping ─> ProgramMetric ─> Health + NBA
```

Важно: Keycloak и `rtk_eduflow` — две разные базы на одном PostgreSQL-сервере. Схема собственных внутренних таблиц Keycloak не является моделью CRM и seed CRM её не заполняет.

## 2. Главная бизнес-единица

`program_instances` — каноническая сущность сделки/внедрения.

Одна запись — это конкретная комбинация:

```text
Организация (вуз/площадка)
  × IT-направление
  × IT-продукт
  × KAM
  × версия workflow / playbook
  × учебное окно
```

Именно `ProgramInstance`, а не организация, имеет текущий этап, здоровье, статус, лицензию, B2C/LMS/Website-сигналы и NBA-действия. У организации не должно быть общего «статуса сделки».

Старый контур `university_interactions` сохранён для совместимости. Новые сценарии должны строиться вокруг `program_instances`; поле `legacy_interaction_id` связывает новую запись с прежним взаимодействием при необходимости.

## 3. Полная карта таблиц

Во всех моделях с типовым набором полей присутствуют `id`, `created_at`, `updated_at`; ниже перечислены предметные поля и связи. `id` — UUID/первичный ключ модели.

### 3.1. Доступ, пользователи и разграничение данных

| Таблица | Содержимое | Основные связи |
|---|---|---|
| `users` | Локальный профиль (`keycloak_user_id`, username, ФИО, email, legacy role, active) | Назначения KAM/руководителей и авторы операций |
| `roles` | Роли CRM | M:N с `users` через `user_roles` |
| `user_roles` | Связь пользователя и роли | `user_id → users`, `role_id → roles` |
| `manager_memberships` | Состав команды руководителя, период действия | `manager_user_id → users`, `kam_user_id → users` |
| `org_assignments` | Закрепление сотрудника за организацией, статус и даты | `organization_id → organizations`, `user_id → users`, `assigned_by → users` |
| `data_access_scopes` | Точечные права на вуз/старое взаимодействие, срок и уровень доступа | user, university, interaction, granting user |
| `responsible_assignment_history` | История смены ответственного в legacy interaction | old/new/changed_by users, `interaction_id` |

Роли, используемые UI/API: `ADMIN`, `MANAGER`, `KAM`. В отчётах scope выводится из роли: KAM видит собственные `ProgramInstance`, MANAGER — назначения KAM своей активной команды, ADMIN — все.

### 3.2. Организации, вузы, люди

| Таблица | Содержимое | Основные связи |
|---|---|---|
| `organization_types` | Справочник типов организаций | 1:N с `organizations` |
| `organizations` | Универсальная площадка: название, short name, регион, город, статус, комментарий | `type_id → organization_types` |
| `stakeholders` | Контакты площадки и/или программы: роль, ФИО, должность, контакты, primary/active | `organization_id`, optional `program_instance_id` |
| `universities` | Legacy-каталог вузов: адрес, сайт, регион/город | Используется legacy interaction-контуром |
| `university_contacts` | Контакты legacy-вуза | `university_id → universities` |
| `interaction_contacts` | Роль контакта в legacy-взаимодействии | `interaction_id → university_interactions`, `contact_id → university_contacts` |

Для нового seed площадки создаются в `organizations` вместе с `organization_types`; `universities` и `university_contacts` нужны только если требуется показать или проверить старый контур.

### 3.3. Продуктовый и образовательный каталог

| Таблица | Содержимое | Основные связи |
|---|---|---|
| `it_directions` | Направления: code, name, description, active | Родитель `it_programs`, используется в `ProgramInstance` |
| `it_programs` | Образовательные программы legacy-каталога | `direction_id → it_directions` |
| `vendors` | Поставщики: name, business_key, description | Родитель продуктов и контактов |
| `it_products` | Продукты: name, business_key, документация, active | `vendor_id → vendors`; участвует в ProgramInstance |
| `program_products` | Связь legacy-программы с продуктом и обязательность | `program_id → it_programs`, `product_id → it_products` |
| `vendor_contacts` | Контакты вендора/продукта, business key, канал связи | `vendor_id`, optional `product_id` |
| `academic_windows` | Учебные периоды: code, title, даты плана/занятий, current | optional `academic_window_id` у ProgramInstance |

### 3.4. ProgramInstance, договорная часть и преподаватели

| Таблица | Содержимое | Основные связи |
|---|---|---|
| `program_instances` | Ядро: организация, направление, продукт, KAM, playbook/version snapshot, current stage, status, health, даты, parent, legacy link | FK на organization, direction, product, KAM user, workflow template/version/stage, academic window, self parent, legacy interaction |
| `contracts` | Договор: номер, сроки, статус, подпись, вложение | optional `interaction_id`, `organization_id`, `attachment_id → files` |
| `licenses` | Лицензия: номер, срок, transfer, product access, дата передачи, вложение | `contract_id`, `product_id`, optional `program_instance_id`, `attachment_id` |
| `teacher_carriers` | Носитель/преподаватель: ФИО, обучение, квалификация, LMS-активность, статус | organization, optional ProgramInstance, product, optional stakeholder |

Лицензия в отчёте выводится как связанная с программой (`licenses.program_instance_id`). Наличие записи о лицензии не заменяет прохождение этапов workflow.

### 3.5. Workflow, playbook и чек-листы

| Таблица | Содержимое | Основные связи |
|---|---|---|
| `workflow_templates` | Playbook: code, имя, версия, область применения, status/default, автор | Родитель версий, stages, transitions |
| `workflow_versions` | Версия playbook, состояние, supersedes, кто/когда опубликовал/архивировал | `workflow_template_id`, self supersedes, author |
| `workflow_phases` | Фазы справочника этапов | Используется stage catalog |
| `workflow_stage_catalog` | Общий справочник кодов/названий этапов | optional default phase |
| `workflow_stages` | Этап конкретной версии: порядок, initial/final/optional, критичность, срок, требования | template, version, optional stage catalog |
| `workflow_transitions` | Разрешённый переход между этапами | template/version, from/to stage |
| `workflow_stage_instances` | Экземпляр этапа по ProgramInstance или legacy interaction: исполнитель, статус, дедлайны | program/interaction, workflow stage, responsible user |
| `workflow_transition_history` | Фактически выполненный переход | program/interaction, from/to stage instance, transition, performer |
| `workflow_stage_comments` | Комментарии к экземпляру этапа | stage instance, author |
| `workflow_stage_attachments` | Прикреплённый к этапу файл | stage instance, file, uploader |
| `playbook_checklist_items` | Требование этапа: тип, обязательность, требуемая роль/вложение | `workflow_stage_id` |
| `program_checklist_values` | Факт заполнения чек-листа: bool/text/number/date, stakeholder, attachment | checklist item, stage instance, optional stakeholder/file |
| `workflow_change_requests` | Запрос изменить опубликованную версию | version, requester/reviewer, опасные изменения |
| `workflow_stage_mappings` | Соответствие этапов при миграции версий | source/target versions and stages, author |
| `workflow_migration_jobs` | Задание миграции: статусы, счётчики, ошибка | versions, change request, creator |

`program_instances.current_stage_instance_id` и `workflow_stage_instances.program_instance_id` образуют преднамеренную двустороннюю связь: программа быстро указывает на текущий этап, а этап хранит владельца. В seed после создания этапов нужно установить оба конца согласованно.

### 3.6. Интеграционные сигналы, здоровье и действия

| Таблица | Содержимое | Основные связи |
|---|---|---|
| `integration_signals` | Сырой и normalized payload, source, external key, время, status, ошибка, причина матчинга | optional `organization_id`, optional `program_instance_id` |
| `external_course_mappings` | Явное соответствие внешнего названия курса направлению+продукту | `direction_id`, `product_id` |
| `external_stream_mappings` | Явное соответствие course+stream конкретной программе | `program_instance_id` |
| `program_metrics` | Агрегат последнего состояния: заявки, студенты, потоки, B2C-записи оплат, teacher activity и timestamps источников | 1:1 (`program_instance_id`) |
| `nba_rules` | Справочник правил Next Best Action | Используется в NBA item |
| `nba_items` | Рекомендованное действие: severity, reason, action, priority, target, срок, status | rule, organization, optional ProgramInstance/product |

`IntegrationSignal` — журнал фактов, не бизнес-итог. `ProgramMetric` — пересчитываемый агрегат mapped сигналов. Затем `HealthService` пересчитывает `health_score`/`health_band` программы, а `NbaService` создаёт или обновляет её `nba_items`.

| `documentation_images` | Изображения в документации | page, file |

## 4. Откуда берутся данные сейчас

| Набор | Реальный источник в демо-контуре | Что попадает в БД | Что является моковым/ограничением |
|---|---|---|---|
| Пользователи и роли | `seed_demo_data.py` + Keycloak realm | CRM `users`, `roles`, `user_roles`, team membership | Демо-учётные записи, не кадровая интеграция |
| Вузы/площадки, каталог, KAM, workflow, договоры | `seed_demo_data.py` | Соответствующие справочники и ProgramInstance | Контролируемый demo seed, но не runtime mock UI |
| Vendor catalog | Загружаемый XLSX/fixture | Vendor, product, vendor contacts и import artefacts | Формат ограничен колонками импорта |
| B2C user list | XLSX/fixture | IntegrationSignal, только external key/ФИО для matching и hash контактов | Не создаёт карточку студента; raw PII не служит CRM-данными |
| B2C/payment | JSON «Данные оплат»/fixture | Payment IntegrationSignal, затем `payment_records_count` только после explicit mapping | Это запись заказа/зачисления, не подтверждённая оплата и не деньги |
| Website | `program_signals.json` в demo | Последний mapped signal → `applications_count` | DEMO fixture, нет живой интеграции сайта |
| LMS | `program_signals.json` в demo | Последний mapped signal → students/streams/teacher activity | DEMO fixture, нет живой LMS-интеграции |
| Отчёты | Реальные ProgramInstance, ProgramMetric, workflow, licenses, KAM | preview и готовый XLS/XLSX/PDF | Legacy «Взаимодействия»/«Менеджеры» UI ещё имеют помеченные `*` mock-наборы |

### 4.1. Контракт входных интеграционных данных

`VENDOR_CATALOG` (XLSX): колонки `Компания`, `Продукт` (может разделяться запятыми), `ФИО`, `Телефон`, `Почта`, `Способ связи`.

`B2C_USER` (XLSX): `Фамилия`, `Имя`, `Отчествопри наличии)`, `Email`, `Номер телефона`. Разрешено использовать только операционные ключи и хеши email/телефона; паспорт, СНИЛС и подобные поля не добавляются.

`PAYMENT` (JSON array): обязательный `Номер заявки`; допустимы `Email`, `Телефон`, `Фамилия`, `Имя`, `Отчество`, `Курс`, `Номер потока`. Для зачёта в ProgramMetric запись должна пройти mapping внешнего курса и потока на ProgramInstance.

`WEBSITE`/`LMS`: на данном этапе file-less fixture `backend/app/modules/integrations/fixtures/program_signals.json`. Сигнал содержит внешний ключ площадки/продукта и показатели. Он не имеет права сам создать ProgramInstance, перевести workflow или закрыть сделку.

## 5. Правила матчинга и агрегации

```text
Внешний файл или fixture
  → adapter: parse / validate / normalize
  → IntegrationSignal (всегда можно сохранить unmatched или invalid)
  → explicit mapping
  → ProgramMetric одной ProgramInstance
  → HealthService + NbaService
```

1. `WEBSITE` и `LMS` ищут точное соответствие organization + product; когда ProgramInstance один, сигнал привязывается к нему.
2. `PAYMENT` требует оба сопоставления: `external_course_mappings` (курс → направление+продукт) и `external_stream_mappings` (курс+поток → ProgramInstance). Иначе это валидный, но `UNMATCHED` сигнал, и он не меняет метрики.
3. Последний mapped Website-сигнал задаёт `applications_count`; последний LMS-сигнал — `students_count`, `streams_count`, `teacher_activity_on`; число mapped Payment-сигналов становится `payment_records_count`.
4. Повторная поставка одного внешнего ключа должна быть идемпотентной: ключ источника + `external_key`, а не новая искусственная запись.
5. Health — score 0–100 с детерминированными штрафами; NBA — детерминированные P0–P4 рекомендации. Ни сигнал, ни оплата не должны неявно менять этап workflow.

## 6. Как расширять `seed_demo_data.py`

### Обязательный порядок

```text
roles/users
→ organization types + organizations + stakeholders
→ directions + vendors + products (+ legacy programs/products при необходимости)
→ academic windows
→ workflow catalog → template → published version → stages/transitions/checklists
→ manager membership / org assignment
→ ProgramInstance
→ WorkflowStageInstance и current_stage_instance_id
→ contracts/licenses/teacher carriers
→ integration mappings → signals → ProgramMetric sync
→ Health recompute → NBA recompute
→ commit
```

Текущий seed именно после основного набора программ вызывает `HealthService.recompute(program.id)`, `NbaService.recompute_program(program.id)` и `IntegrationSyncService.sync_program(program.id)` для каждой ProgramInstance.

### Минимальная жизнеспособная программа

Для одной новой площадки, которая должна корректно появиться на главной, в вузах и в реальном отчёте, нужны как минимум:

1. `organization_type` и `organization`;
2. существующие или новые `it_direction`, `vendor`, `it_product`;
3. KAM в `users`, а для manager view — активная строка `manager_memberships`;
4. опубликованные `workflow_template` и `workflow_version`, хотя бы один initial `workflow_stage`;
5. `program_instance` с этими FK и ожидаемым `status`;
6. `workflow_stage_instance` с `program_instance_id`, после чего его `id` записывается в `program_instance.current_stage_instance_id`;
7. по необходимости `license`, `stakeholder`, `teacher_carrier`, `academic_window`;
8. `ProgramMetric` либо mapped `IntegrationSignal`; затем обязательный пересчёт Health и NBA.

### Что безопасно симулировать

- демо-организации, продукты, workflow и их этапы;
- KAM/Manager, их команды и назначения;
- этапы, дедлайны, комментарии, чек-листы, договоры и лицензии;
- тестовые Website/LMS snapshots, если в названии/экране остаётся признак `*` или `DEMO`;
- нейтральные B2C payment records с внешним ключом, курсом и потоком без финансовых сумм;
- полностью mapped и намеренно unmatched/invalid сигналы для диагностики;
- report jobs/artifacts, NBA и audit events как результаты сценария.

### Что нельзя выдумывать или трактовать как факт

- деньги, сумму/валюту/дату/успешность оплаты — в текущем контракте их нет;
- данные студентов как отдельные CRM-профили или чувствительные персональные данные;
- автоматическое создание/закрытие ProgramInstance на основании Website/LMS/B2C файла;
- автоматический переход workflow из факта оплаты, заявки или LMS-активности;
- общий статус сделки на `organization` вместо состояния конкретной ProgramInstance;
- B2C aggregates в отчётах как финансовые KPI: это только operational signals.

## 8. Проверка seed перед использованием

1. Не создаётся ли duplicate по бизнес-ключам (`code`, `business_key`, external key), если seed запускается повторно.
2. У каждой ProgramInstance заполнены существующие FK на organization, direction, product, KAM и published workflow version.
3. `current_stage_instance_id` принадлежит той же программе и соответствует `current_stage_code`.
4. У manager scope есть активная `manager_memberships`, у KAM — доступная ProgramInstance.
5. Все demo LMS/Website/B2C данные имеют понятный признак DEMO/`*`, если идут на экран.
6. Для payment metrics существуют оба external mapping; намеренно unmatched записи сохранены как диагностика, но не попали в счётчики.
7. После добавления сигналов выполнены `IntegrationSyncService`, `HealthService`, `NbaService`.
8. Если добавлен файл, одновременно есть объект в нужном MinIO bucket и строка `files`/связанная artifact-таблица.

## 9. Не покрыто текущим контуром

- Нет реального коннектора к Website или LMS: они демонстрационные fixtures.
- Нет student CRM и финансового биллинга; `payment_records_count` — количество сопоставленных B2C-записей, не выручка и не подтверждённая оплата.
- В frontend не реализован полноценный пользовательский кэш бизнес-данных; Redis используется очередью report worker, а не кэшем страниц.
- Часть старого функционала — `university_interactions` и два legacy report types — сохранена ради совместимости. Для новых данных предпочтителен контур `ProgramInstance`.
