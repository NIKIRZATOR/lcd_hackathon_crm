# Модуль документации

## Назначение

Модуль выводит контекстную справку в правой выдвижной панели V2, позволяет ADMIN редактировать статьи и Markdown-файлы, загружать изображения, а пользователям — создавать обращения по документации.

Основной UI:

- кнопка `?` в V2-header открывает панель;
- раздел выбирается автоматически по текущему frontend-маршруту;
- доступны разделы «Главная», «Организации», «Воркфлоу», «Отчёты» и, только для ADMIN, «Управление»;
- ADMIN видит обращения на странице `Управление → Обращения`.

## Роли

| Действие | KAM | MANAGER | ADMIN |
| --- | --- | --- | --- |
| Читать статьи и изображения | Да | Да | Да |
| Создать обращение | Да | Да | Да |
| Смотреть все обращения | Нет | Нет | Да |
| Менять статус обращения | Нет | Нет | Да |
| Создавать/редактировать статьи | Нет | Нет | Да |
| Загружать Markdown и изображения | Нет | Нет | Да |

Backend всегда проверяет роли через `require_roles`; скрытая кнопка во frontend не является защитой.

## Сущности и таблицы

Все сущности используют UUID `id`, `created_at`, `updated_at` из `ModelBase`.

### `documentation_pages`

Статья или узел дерева документации.

| Поле | Назначение |
| --- | --- |
| `slug` | Уникальный технический идентификатор, допускаются строчные латинские буквы, цифры и `-`. |
| `title` | Название статьи/раздела. |
| `route_pattern` | V2-маршрут, с которым сопоставляется статья, например `/v2/organizations`. |
| `parent_id` | Ссылка на родительскую статью для дерева. |
| `sort_order` | Порядок в дереве. |
| `content_markdown` | Markdown-содержимое, которое рендерится в панели. |
| `source_file_id` | Последний исходный `.md` файл в таблице `files`; устанавливается при загрузке файла. |

Ограничения: `slug` уникален; есть индекс по `route_pattern`.

### `documentation_images`

Связь статьи с файлом изображения.

| Поле | Назначение |
| --- | --- |
| `page_id` | Статья-владелец; при её удалении связь удаляется каскадно. |
| `file_id` | Запись в общей таблице `files`; уникальна для этой связи. |

### `documentation_requests`

Обращение пользователя по статье.

| Поле | Назначение |
| --- | --- |
| `page_id` | Необязательная статья, из которой создано обращение. |
| `author_user_id` | Обязательный пользователь-автор. Устанавливается backend из текущей Keycloak-сессии, не передаётся клиентом. |
| `subject` | Тема, от 3 до 255 символов. |
| `message` | Полный текст, от 3 до 10 000 символов. |
| `status` | `open` или `closed`. |

Есть индекс по `(status, created_at)` для списка обращений.

## Файлы и MinIO

Используется существующая файловая инфраструктура: метаданные находятся в `files`, бинарные данные — в MinIO/S3-совместимом хранилище.

- bucket: настройка `S3_BUCKET_DOCUMENTATION`, значение по умолчанию `documentation`;
- исходный Markdown: `documentation/{page_id}/{uuid}.md`;
- картинка: `documentation/{page_id}/images/{uuid}.{ext}`.

Поддерживаемые форматы изображений: PNG, JPG/JPEG, WEBP, GIF. Размер ограничен глобальной настройкой `FILE_MAX_UPLOAD_BYTES`. Бинарное содержимое картинки отдаётся только авторизованным пользователям CRM через защищённый API; прямой публичный URL MinIO не используется.

## Markdown

Статья хранится как текст Markdown. В текущем renderer поддерживаются заголовки `#`–`###`, абзацы, маркированные строки `- ...`, поиск с подсветкой и ссылки на внутренние картинки.

После загрузки картинки API возвращает готовую строку:

```md
![diagram.png](doc-image://{image_id})
```

Frontend вставляет её в поле Markdown. При просмотре строка преобразуется в защищённую загрузку изображения.

## API

Все пути ниже начинаются с `/api/documentation`. Все запросы требуют Bearer JWT.

### Статьи

| Method, path | Роли | Назначение |
| --- | --- | --- |
| `GET /pages` | CRM | Дерево всех статей, отсортированное по `sort_order`, затем `title`. |
| `GET /pages/for-route?route=/v2/organizations` | CRM | Находит наиболее специфичную статью для маршрута. |
| `POST /pages` | ADMIN | Создаёт статью. |
| `PATCH /pages/{page_id}` | ADMIN | Изменяет заголовок, маршрут, родителя, порядок и/или Markdown. |
| `POST /pages/{page_id}/upload` | ADMIN | Загружает UTF-8 `.md`/`.markdown`, обновляет `content_markdown` и `source_file_id`. |

Пример обновления текста:

```json
PATCH /api/documentation/pages/{page_id}
{
  "title": "Организации",
  "content_markdown": "# Организации\n\nИнструкция..."
}
```

### Изображения

| Method, path | Роли | Назначение |
| --- | --- | --- |
| `POST /pages/{page_id}/images` | ADMIN | `multipart/form-data`, поле `file`; сохраняет изображение. |
| `GET /pages/{page_id}/images/{image_id}` | CRM | Потоково отдаёт изображение с проверкой доступа. |

Успешная загрузка возвращает:

```json
{
  "id": "image-uuid",
  "file_id": "file-uuid",
  "markdown": "![diagram.png](doc-image://image-uuid)"
}
```

### Обращения

| Method, path | Роли | Назначение |
| --- | --- | --- |
| `POST /requests` | CRM | Регистрирует обращение от текущего пользователя. |
| `GET /requests` | ADMIN | Список всех обращений, включая `author_name`. |
| `PATCH /requests/{request_id}` | ADMIN | Меняет статус на `open` или `closed`. |

Пример создания обращения:

```json
POST /api/documentation/requests
{
  "page_id": "page-uuid",
  "subject": "Неясно, как создать программу",
  "message": "Нужна инструкция для раздела Организации."
}
```

Frontend ждёт успешный HTTP-ответ перед закрытием формы. При `2xx` показывает «Ваше обращение зарегистрировано». Для `401`, `403`, `422` и прочих ошибок выводится отдельное сообщение; форма при ошибке остаётся открытой.

## Пользовательские сценарии

### Просмотр документации

1. Пользователь нажимает `?` в header.
2. Панель запрашивает список статей и статью для текущего маршрута.
3. Открывается соответствующий раздел; поиск фильтрует дерево и подсвечивает совпадения в тексте.

### Редактирование статьи ADMIN

1. ADMIN открывает шестерёнку в правом верхнем углу статьи.
2. Выбирает редактирование Markdown либо замену `.md` файла.
3. При необходимости через форму добавляет изображение: Markdown-ссылка вставляется автоматически.
4. Нажимает «Сохранить»; новый Markdown становится содержимым статьи.

### Работа с обращением ADMIN

1. ADMIN открывает `Управление → Обращения`.
2. Использует фильтры по тексту, статусу и дате.
3. В компактном реестре длинные значения обрезаются `…`.
4. Клик по строке открывает карточку с полным текстом, автором, датой и селектором статуса.
